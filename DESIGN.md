## Problem Statement

Gearing decisions in modern WoW require leaving the game, pasting a `/simc` export into Raidbots or SimulationCraft, parsing a dense HTML report, and translating the results back into in-game actions ("oh, my best flask is X"). The cognitive cost is high enough that most players either skip simming entirely or default to whatever a class Discord told them weeks ago.

Craft Compass closes the loop. The player asks concrete questions in-game ("what flask should I use?", "best dungeon to farm voidcores for upgrades?", "BiS for heroic-only?") and gets answers as tooltips and an in-game panel. A companion desktop app runs SimulationCraft locally and writes the answers back into the addon.

## What Makes This Cool

- **Tooltip-driven answers.** Hover a flask in your bag and see "Craft Compass: best flask for your current setup, +1.2% DPS over Phial of Tepid Versatility." No tab-out, no HTML parsing.
- **Questions framed the way players actually think.** Not "DPS by item permutation." Instead: "Which dungeon should I push for upgrades?" The sim is the engine, not the interface.
- **Nobody else does this.** The SimC addon exports profiles; nothing exists that takes sim *results* back into the game. Raidbots is a website. AskMrRobot is a website. The community gap (sim devs and addon devs are different crowds) is the whole reason this niche is empty.

## Constraints

- **Midnight (12.0) addon rules.** Combat decision automation is restricted (Secret Values, WeakAuras retail discontinuation). Utility addons — including tooltip recommendations and gearing advice — are explicitly fine. Craft Compass is utility; it stays in bounds.
- **Reload friction.** WoW addons have no live IPC. Companion-app→addon and addon→companion-app both require `/reload` (or logout) to flush. Realistic flow is 1-2 reloads per query cycle. Not optional; design accommodates it.
- **Solo player, local files only.** No accounts, no cloud, no data sharing. Just files in the WoW WTF folder and a local SimC binary.
- **Side project budget.** Built for fun, not for funding. Keep maintenance load small; lean on existing data sources rather than scraping/curating from scratch.

## Premises

1. **In-game answers are the wedge** — not better/faster sims. If recommendations show up anywhere other than inside WoW, the differentiator vanishes.
2. **1-2 /reloads per query cycle is acceptable friction.** Players already /reload regularly; framing the flow around it is honest UX.
3. **Curated answer set, not a generic platform.** v1 ships:
   - Best consumables (flask / pot / food / phial / weapon enchant)
   - Best gems for current gear
   - Best dungeon to farm for upgrades (currency-aware: voidcores, etc.)
   - BiS list filtered by player's difficulty (heroic-only, mythic, M+ key range)
   - Best embellishments / crafted item slot decisions
4. **Bundle upstream SimC, don't fork.** Desktop app downloads SimC binaries from GitHub Releases. Pin a "known good" version with a "use latest / use pinned" toggle to insulate against bad APL updates.
5. **Local-only, single player.** No multi-character syncing, no cloud sync, no shared raid data. Future scope, not v1.
6. **Data layer = SimC's generated DB + cribbed dungeon mapping + small per-patch curation.** SimC ships item/stat data already aligned to its own engine. KeystoneLoot's dungeon→drops table can be cribbed (open addon). Currency mappings (voidcores per dungeon, etc.) need manual per-patch updates — small enough load for a side project.

## Approaches Considered

### Approach A: Hardcoded query suite, minimal addon
Desktop tray app + minimal addon. Fixed set of questions baked in code. Tooltip injection via `GameTooltip:SetItem` hook. Fastest to playable.

### Approach B: Schema-driven question catalog
Same plumbing, but every question is a JSON/Lua definition shipped in a separate catalog. Community-extensible. Rejected for v1: massively overengineered for a project with no audience yet.

### Approach C: Headless desktop, in-game is the entire UI
Desktop is a tray icon only. All interaction happens via an in-game panel. Fully commits to the wedge.

## Recommended Approach

**Build A first, evolve toward C, keep desktop UI as a power-user "deep dive" view.**

A ships fast (1-2 weekends to MVP). It proves the plumbing works end-to-end before any UI commitment. Once the data flow is solid, the addon side grows: a `/wowsim` slash command, an in-game panel for picking questions, settings UI for which questions to enable per spec.

The desktop UI never gets thrown away — it transitions from "the primary interface" to "the deep-dive interface." Casual users live in the addon (tooltips, panel). Theorycrafters open the desktop app to see the full SimC report behind a recommendation, queue depth, sim history, raw output.

### Data flow (target architecture)

```
WoW client                         Desktop tray app
    │                                     │
    │  /reload or /logout                 │
    ├──── writes simc export ──────────► │ (file watcher: chokidar)
    │     to SavedVariables              │
    │                                    ├──► spawns SimC subprocess
    │                                    │    runs question suite
    │                                    │    (best flask, best gems, ...)
    │                                    │
    │                       writes Lua  │
    │  ◄────── results table to ────────┤
    │          addon folder              │
    │                                    │
    │  /reload                           │
    ├──► reads results from SavedVariables
    │    addon updates tooltips + panel
```

### Tech stack

- **Desktop app:** Node.js + Electron OR Tauri (smaller binary, Rust core). Tauri is the better long-term call if you don't need heavy Electron-specific features. Either way: `chokidar` for file watching, `luaparse` (Node) or `slpp` (Python — if you go Python route) for parsing SavedVariables.
- **Addon:** Standard Lua addon. Bundle the SimC addon's export module as a vendored dependency (MIT-licensed, recompute-cheap). Hook `GameTooltip:SetItem` for tooltip injection.
- **SimC binary:** Downloaded from `https://github.com/simulationcraft/simc/releases` on first run. Pinned version stored in app config; auto-update toggle.
- **Data:** SimC's `engine/dbc/generated/` for item/stat data. Crib KeystoneLoot's dungeon→drops Lua table. Hand-curated `currencies.lua` for voidcore/etc. mappings each patch.

## Open Questions

- **Exact KeystoneLoot data format.** Need to actually read its addon files to confirm it ships baked-in static tables vs. computing dynamically. (Quick verification task before committing to the cribbed-data plan.)
- **Voidcore / Midnight currency drop mappings.** Confirm the actual currency name(s) and drop sources at Midnight launch — terminology may shift. ([Wowhead Midnight database](https://www.wowhead.com/) is the source of truth here.)
- **Tooltip hook conflicts.** Other addons (LeatrixPlus, TipTac, etc.) heavily modify tooltips. Need to use `TooltipDataProcessor.AddTooltipPostCall` (the modern post-Dragonflight API) and test against common tooltip-modifying addons.
- **Multi-character / multi-spec handling.** v1 = active character, active spec only. Multi-spec stored as separate result blobs in SavedVariables; addon picks the right one on load.
- **SimC sim duration.** Each "question" is multiple sims. A 5-question suite at 10K iterations could take 5-15 minutes on a typical machine. Need to either run shorter sims (3K iters, accept noise), parallelize, or queue with progress shown in the desktop tray and in-game panel.

## Success Criteria

**MVP (Approach A complete):**
1. Install addon + desktop app on a fresh machine in under 5 minutes.
2. Open WoW, /reload — addon writes simc export to SavedVariables.
3. Desktop app sees the file change, runs at least one sim ("best flask"), writes result.
4. /reload again — tooltip on a flask shows "Craft Compass: best flask = X."

**v1 (toward Approach C):**
1. `/wowsim` opens an in-game panel with the full question list.
2. Picking a question queues it without a /reload (request goes to SavedVariables; runs at next /reload).
3. All five v1 question types (consumables, gems, dungeon, BiS, embellishments) work end-to-end.
4. Desktop app has a "deep dive" view showing the full SimC HTML report behind any recommendation.

## Distribution Plan

- **Addon:** CurseForge + Wago Addons. Standard CI: GitHub Actions workflow that bumps the .toc file, packages the addon, uploads to both. ([CurseForge upload action](https://github.com/marketplace/actions/upload-to-curseforge))
- **Desktop app:** GitHub Releases hosting Windows installer (NSIS or MSI), Mac DMG (signed if you're willing to pay 9/yr for an Apple Developer cert; otherwise users right-click-open), Linux AppImage. CI: same GitHub Actions workflow, builds all three on each tagged release.
- **First release:** Windows-only is fine. Mac/Linux when there's demand.
- **No web service, no backend.** Nothing to deploy beyond static binaries.

## Next Steps

Concrete build order:

1. **Spike: prove the round-trip works.** Write a 50-line Node script that watches a SavedVariables file and rewrites a result file in an addon folder. Write a 50-line addon that reads the result file. Confirm the loop end-to-end before building any UI.
2. **Vendor SimC export logic into your addon.** Strip the SimC addon down to its export module; trigger it on `PLAYER_LOGOUT`; stuff the export string into SavedVariables.
3. **Spawn SimC from the desktop app.** Bundle a SimC binary, run it as subprocess with the exported profile + a single hardcoded "best flask" simulation. Parse the output.
4. **Write results back as a Lua data table.** Format: `Craft CompassResults = { flask = { best = "Phial of...", delta = 1.024 }, ... }`. Drop into addon folder.
5. **Tooltip hook for flasks.** `TooltipDataProcessor.AddTooltipPostCall(Enum.TooltipDataType.Item, function(tooltip, data) ... end)`. Match item ID against the result table. Add a line.
6. **Add the second question (gems).** Confirm the architecture extends cleanly.
7. **Add the desktop UI for sim status / queue.**
8. **Crib KeystoneLoot's data and add the dungeon-farm question.**

After step 6 you have a real, working, demoable product. Steps 1-6 is the realistic "first big push." Everything after is iteration.
